# DeskLink v1.0.3

DeskLink v1.0.3 重点解决“能连接但黑屏/视频卡死难定位”“弱网鼠标拖尾”和“生产服务器表面健康但认证实际不可用”这几类影响真实使用的问题。

## Windows：新增 GPU 媒体管线实测探针

Windows 发布包新增：

- `desklink-media-probe.exe`

它不是简单查询显卡型号，而是实际走一遍 DeskLink 当前的视频链：

1. 创建 D3D11 硬件设备；
2. 初始化 DXGI Desktop Duplication；
3. 枚举并检查显示器；
4. 将桌面 BGRA 纹理通过 GPU Video Processor 转换为 NV12；
5. 初始化 Media Foundation 硬件 H.264 Encoder；
6. 实际输出一个 H.264 access unit。

如果桌面长时间静止、Desktop Duplication 暂时没有新帧，探针会创建 GPU 测试纹理继续验证 NV12/H.264，避免把“桌面没变化”误判为显卡故障。

`DeskLink.exe` 的“连接诊断”现在会自动调用该探针，并把失败点直接翻译成中文，例如：

- D3D11 硬件设备不可用；
- DXGI Desktop Duplication 初始化失败；
- GPU BGRA → NV12 路径不可用；
- 没有兼容的硬件 H.264 编码器；
- 编码器初始化成功但无法实际输出视频帧。

这样“网络正常但没有画面”可以直接区分是采集、GPU 转换、编码器还是网络/Signal/TURN 问题。

媒体探针在管理器中有执行超时，不会因为异常驱动长期卡住设置窗口；诊断报告仍不会包含访问码或 `dc2` 明文。

## Windows：硬件 H.264 编码器防永久卡死

此前异步 Media Foundation MFT 使用阻塞式事件等待。如果显卡驱动/硬件编码器异常后不再发送 `NeedInput` 或 `HaveOutput`，视频线程存在永久停住的风险。

v1.0.3 改为：

- Media Foundation event 使用非阻塞轮询；
- 单次事件等待上限约 750 ms；
- `NeedInput` / `HaveOutput` 超时不再无限等待；
- `ProcessInput` / `ProcessOutput` 异常触发流恢复；
- 自动执行 MFT Flush；
- 重新发送 `START_OF_STREAM`；
- 恢复后请求关键帧。

目标是让一次显卡编码器抖动退化为短暂丢帧/恢复，而不是整个远控画面永久停止。

## Windows CI：完整四 EXE 产物

普通 Windows CI artifact 现在包含：

- `DeskLink.exe`
- `desklink-agent.exe`
- `desklink-service.exe`
- `desklink-media-probe.exe`

媒体探针同时参与 portable dependency 检查。Release 包、SHA-256 校验和可选 Authenticode 签名流程也包含该 EXE。

## Web：弱网时丢弃已经过期的鼠标移动

DeskLink 原本已经将鼠标移动放在独立的 unordered / unreliable WebRTC DataChannel 中，按键、鼠标按下/抬起则继续使用可靠控制通道。

v1.0.3 在此基础上增加浏览器本地 SCTP 背压保护：

- `pointer` 通道本地 `bufferedAmount` 超过约 8 KiB 时；
- 只丢弃已经没有价值的旧 `pointer move`；
- 新坐标继续采用 latest-wins；
- 不丢弃鼠标 down/up；
- 不丢弃键盘、滚轮、release-all 等可靠控制事件。

这主要改善高 RTT、丢包或带宽突降时的“鼠标轨迹拖着走”问题，避免旧坐标排队增加控制尾延迟。

低延迟补丁同时增加 WebRTC 全局对象 feature detection，确保不支持 WebRTC 的浏览器仍能进入 DeskLink 自己的兼容性提示，而不是模块加载阶段直接报错。

## Signal：新增认证感知的 `/readyz`

`/healthz` 继续用于证明 Go 进程本身存活；新增 `/readyz` 用于证明生产认证链真正可用。

生产 readiness 会检查：

- device credential registry 能否读取并完整解析；
- controller credential registry 能否读取并完整解析；
- device revocation 状态能否读取；
- Signal Auth Secret 是否存在；
- TURN REST Secret 是否存在；
- 生产模式要求的 registry 是否确实配置。

失败时返回 HTTP 503，而不是让容器继续显示 healthy、等用户登录时才发现所有设备都无法认证。

开发模式仍保持兼容：未开启生产 readiness 强制项时，不要求必须部署完整 registry/TURN 认证链。

## 生产 Compose：健康状态真正代表“可登录”

生产 Signal 容器健康检查从 `/healthz` 升级到 `/readyz`。

同时生产 Compose 会从当前仓库源码构建 Signal，避免出现“Compose 已经要求 `/readyz`，但 `latest` 镜像还是旧版本”的 API/镜像版本错配。

`Deployment Smoke` 也从只检查配置/镜像构建升级为真实运行测试：

1. 执行真实 `bootstrap.sh`；
2. 启动 Signal 容器；
3. 等待 `/readyz` 变为 healthy；
4. 验证正常 registry 返回 `ok=true`；
5. 故意破坏 `devices.json`；
6. 验证 `/readyz` 必须失败。

因此 registry 格式、挂载路径或认证配置被后续改坏时，CI 会直接阻断。

## 生产 Bootstrap：修复 root-owned registry

此前 Bootstrap 内部通过 Docker 运行 Go 凭证工具时使用容器默认 root 用户，生成的 `devices.json` / `controllers.json` 可能在宿主机变成 root 所有，导致普通部署账户后续 `chmod`、轮换凭证甚至 bootstrap 本身失败。

现在工具容器使用调用者的宿主机 UID/GID 写文件，并将 Go HOME/GOPATH/GOCACHE 放到容器 `/tmp`。

因此：

- registry 文件保持部署用户所有；
- `chmod 444` 可以正常执行；
- 后续凭证轮换不需要因为文件属主问题改用 root；
- 真实 Deployment Smoke 已覆盖这条路径。

## 生产反代：限流继续按真实客户端 IP 生效

生产链仍使用 Caddy → Nginx → Signal。Nginx 会清理可伪造的客户端 IP 头，再转发受控的 `X-Forwarded-For`；Signal 在生产 Compose 中显式信任这条代理链。

这样 WebSocket 握手限制和认证失败封禁按真实客户端 IP 工作，不会把所有浏览器错误地视为同一个 Nginx 容器 IP。

## Windows SmartScreen

v1.0.3 的 Release 流程继续支持对四个 Windows EXE 做 Authenticode SHA-256 签名。

但是仓库当前仍未配置受 Windows 信任的 OV/EV 代码签名证书，因此自动发布的测试包仍可能显示“未知发布者 / Windows 已保护你的电脑”。这一点必须通过正式代码签名证书解决，程序代码本身不能伪造可信发布者身份。
